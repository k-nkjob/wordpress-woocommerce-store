# KNKJOB STORE — WordPress / WooCommerce EC Portfolio

WordPress / WooCommerce で構築した自主制作ECサイトです。  
WooCommerceを導入して終わりではなく、**商品登録・在庫・バリエーション・配送・クーポン・デモ注文・受注確認まで実際に操作し、そこで見つかった問題を原因調査して改善する**ことを目的に制作しました。

また、開発支援としてAIを利用しています。ただし生成コードをそのまま採用するのではなく、ブラウザ表示・DevTools・WooCommerce管理画面・公開環境で動作を確認し、効かなかった修正は原因を追い直して設計自体を変更しています。

## 独自カスタマイズ

### 1. パンくず導線の改善

変更前:

`ホーム → Tops → 商品`

変更後:

`ホーム → ショップ → Tops → 商品`

WooCommerce の `woocommerce_get_breadcrumb` filter を利用し、「商品詳細からショップへ戻りづらい」という実操作上の問題を改善しました。

### 2. ECトップページ

WooCommerceの商品情報を利用して、専用トップページを構築しました。

- Hero
- 商品カルーセル

### 3. 商品一覧 / Cartの商品カード

また、`カートに追加` / `オプションを選択` / `続きを読む` のように用途が異なるボタンでも、レイアウトが崩れないようボタン領域を統一しています。

- 商品編集画面への Material / 発送目安フィールド追加

### 5. デモサイト向け制御

- 新規アカウント作成を無効化

## 開発中に発生した問題と改善

### WooCommerce CSV移行で商品画像がImportできない

InfinityFreeの商品画像URLをLocalWP側から取得しようとした際、`Forbidden` となり、バリエーション商品のImportに失敗しました。

**調査:** Import履歴から画像取得が失敗点であることを特定。  
**対応:** CSVの画像列だけをImport対象外にして商品データを再Importし、画像はLocal環境で再設定。  
**結果:** 親商品1件 + 6バリエーションを正常に移行できました。

### 「ライブ」に変更してもComing Soon画面が表示され続ける

WooCommerce設定、内部オプション、トランジェントを確認しても設定値は公開状態でした。

**調査:** ログイン中は本体が見える一方、ログアウト状態では古いComing Soonページが表示される点からキャッシュを切り分け。  
**原因:** W3 Total Cache がComing Soon時のページをゲスト向けに保持していました。  
**対応:** キャッシュプラグインを無効化して再確認。  
**結果:** ログアウト状態でも公開ECサイトを閲覧できるようになりました。

### スマホの商品カードだけ高さが揃わない

初期対応ではCSSの固定高さを追加しましたが、PCだけ改善し、スマホでは解消しませんでした。

**再調査:** レスポンシブCSS、親Grid、DOM、JavaScriptの列判定まで確認。スマホ用CSSの競合や列数判定の問題を切り分けました。  
**改善:** 「2商品固定」の処理をやめ、表示行ごとにカード要素を扱う方式へ変更。ボタン文言も含めて共通化しました。

### 修正を重ねるほど別ページへ副作用が出る

当初は1つのCSS / JavaScriptへ修正を追加していたため、Shopの調整がCartやHomeへ影響する状態になりました。

**問題:** ページ固有の責務と共通処理が混在しており、原因調査の範囲が広すぎる。  
**改善:** Home / Shop / Product / Cart / Checkout / My Account / Shell をページ・責務単位で分離し、共通処理は汎用ライブラリとして切り出す方針へ変更しました。

この結果、たとえばCartの問題はCartモジュールを中心に確認でき、Homeを修正するためにShopやCartまで同時変更する必要がない構造を目指しています。

### ヘッダーとHomeの横幅が揃わない

テーマ側のHeader / Footerには独自の `max-width` やpaddingを持つ複数ラッパーがあり、外側からCSSを追加するだけでは横幅が安定しませんでした。

**改善:** テーマDOMへの依存を減らし、ストア用Shellと共通コンテナ幅をカスタマイズ側で管理する設計へ変更。Header / Home / Shop / Product / Cart / Checkout / My Account / Footer の横ラインを共通化しました。

## AIを利用した開発と修正プロセス

この制作ではAIを、コード生成だけでなく **既存コード解析・原因候補の整理・修正案作成・リファクタリング補助** に使用しました。

一方で、AIの成果物についても以下の手順で確認しています。

1. AIが修正案を生成
2. LocalWP / InfinityFreeで実際の画面と操作を確認
3. 改善しない場合は、同種のCSSを追加し続けず原因範囲を拡大
4. 子要素 → 親レイアウト → media query → DOM → JavaScript の順で切り分け
5. 一時的なパッチでなく、必要なら責務分離やアーキテクチャを再設計
6. PHP / JavaScriptの構文確認と主要画面の回帰確認

特にレスポンシブ調整では、AI生成の初期パッチだけでは問題が解消しないケースがありました。そこで「効かなかった」という結果も検証材料として使い、最終的にページ単位のモジュール化や共通レイアウト基盤へ改善しています。

**AIを使って速くコードを書くことより、生成結果を検証して修正できることを重視しています。**

## アーキテクチャ方針

カスタマイズは、機能の影響範囲を限定できるよう責務を分けています。

- Shell — Header / Footer / 全体ナビゲーション
- Home — Hero / 商品カルーセル / Latest products
- Archive — Shop / Category / Tagの商品一覧
- Product — 商品詳細 / 商品仕様 / 在庫表示
- Cart — Cart / レコメンド商品
- Checkout — Checkout
- Account — My Account / デモ用登録制御
- Breadcrumb — WooCommerceパンくず

共通処理についても、ページを勝手に横断して変更するのではなく、各モジュールから明示的に利用する構成を意識しています。

## ポートフォリオとして示したいこと

この制作で重視したのは、WordPressやWooCommerceを「使ったこと」だけではありません。

- 既存機能を理解して必要なHookを探す
- 実際に操作して問題を見つける
- 不具合を再現して原因を切り分ける
- AI生成コードも含め、効かなければ原因を再調査する
- 修正の副作用が増えたら設計を見直す
- Localと公開環境の差を確認する
- 最終的に購入フローまで通して確認する

という、既存システム改修・不具合修正に近い進め方を意識しています。
